SPEC‑01

System overview

Each unit runs two loosely-coupled subsystems that share a physical location but not a single point of failure: a unit controller handling alarm, safety lighting, environmental sensors, and telemetry; and a standalone cellular camera handling live/PTZ video independently. Both report to a shared cloud backend, which is the only place their data is correlated.

Three independent uplinks (controller, lock, camera) converge only at the backend — no direct wiring between them.

That separation is deliberate: a standalone smart padlock and a self-contained cellular camera are both off-the-shelf hardware with their own power and connectivity, so neither has to be wired into the controller. The tradeoff, worked through in Sec. 04 and Sec. 05, is that correlating "was this door opened with a valid code" or arbitrating PTZ control happens in software at the backend, not in a local wire.

SPEC‑02

Unit controller

The controller is the only always-on, hard-wired component in the unit. It owns the alarm, the safety lighting, and every sensor except the lock and camera.

Hardware

  • MCU: ESP32-class, running a real-time OS or bare-metal event loop, handling all sensor GPIO and the two relay outputs (siren, lighting).
  • Cellular + GPS: Blues Wireless Notecard (Cell+GPS variant), bridged to the MCU over I2C. A pre-certified, mass-produced module rather than a custom cellular design — offloads the highest-risk, highest-cost part of the build (RF certification, carrier registration, antenna tuning) to hardware that's already proven in the field. Its built-in GNSS also covers the GPS/movement-tracking sensor (Sec. 03) directly, so no separate GPS module is needed.
  • Enclosure: IP65+ weatherproof, vented for the battery, mounted inside the container near the door for direct sensor wiring runs.
  • Power bus: single 12V DC bus off the battery, with a buck converter stepping down to 3.3V/5V logic rails for the MCU and sensors.
  • Local storage: onboard flash or a small SD card for the store-and-forward event buffer (Sec. 10).

Firmware state machine

  • BOOTSelf-test on power-up: verify sensor bus, battery voltage, cellular modem registration. Fails to FAULT on any check failure.
  • ARMED_SETUPSetup window active. Door-open expected and not alarmed; still logged and reported.
  • ARMED_SEALEDUnit sealed, no access window open. Any door-open event immediately escalates to ALARM.
  • ARMED_REMOVALRemoval window active — same posture as ARMED_SETUP, different reporting context.
  • ALARMSiren and strobe drive immediately and locally, independent of connectivity (Sec. 10) — the network report is best-effort, the local response is not.
  • FAULTSelf-test or runtime health check failed. Alarm/lighting outputs held in their last safe state; controller reports fault and awaits remote diagnosis or reset.

Behavior

  • Heartbeat: periodic keepalive publish every 5 minutes — a missed heartbeat is what the backend treats as a lost-controller fault, not a special "I'm dying" message the controller has to send.
  • Watchdog: hardware watchdog timer resets the MCU on firmware hang; state machine re-enters BOOT and re-asserts the last known armed state from local flash.
  • OTA updates: signed firmware images pulled from the backend on a maintenance window, staged to a secondary flash partition, only committed after a successful post-update self-test — failed boot rolls back automatically.

SPEC‑04

Lock integration

The leading lock candidate is a standalone smart padlock — its own battery, its own Bluetooth/PIN access, no wired connection to the controller. That means "was this door opened with a valid code" can't be answered locally; it has to be answered by correlating two independent event streams at the backend.

Model A — Cloud-correlated (default)

  • Lock reports unlock events to its own vendor cloud/API.
  • Controller reports the door-open sensor event independently.
  • Backend matches the two within a 30-second tolerance window to classify the open as authorized or not.
  • No new wiring; works with the current lock candidate as-is.
  • Risk: a connectivity outage on either side during the correlation window can misclassify — needs an explicit fallback rule (Sec. 10).

Model B — Hardwired signal

  • Lock exposes a dry-contact or GPIO output on valid code entry, wired directly to the controller.
  • Instant local correlation, no network round-trip, works fully offline.
  • Requires different lock hardware — most standalone battery smart padlocks, including the current candidate, don't expose a wired output. This means swapping to an integrated electronic deadbolt/strike.

Default to Model A given the current hardware candidate. Revisit Model B only if the lock hardware choice changes toward an integrated (wired) unit — this is one of the open items in Sec. 12.

SPEC‑05

Camera subsystem

The camera candidate is a self-contained cellular PTZ unit with its own SIM and its own vendor cloud — architecturally independent of the controller, the same way the lock is.

Integration approach

Relay through backend media server

  • Backend authenticates to the camera vendor's API with service credentials, pulls the stream, re-serves it to viewers through the platform's own media server (e.g. an RTSP/WebRTC relay).
  • Full control over concurrent-viewer scaling and over the PTZ control-arbitration queue (token-based lock, TTL, preemption on a new request).
  • Adds real infrastructure to run and pay for — cost and bandwidth scale with concurrent viewers.

Embed vendor's viewing widget

  • Lower engineering lift — no media server to run.
  • Limited or no control over PTZ arbitration behavior; tied to whatever the vendor's SDK/widget supports.

The relay approach is the only one that supports true first-come-first-served PTZ arbitration with a hard cutoff when another viewer requests control — recommended default, contingent on confirming the camera vendor exposes an API suitable for relaying (Sec. 12).

Safety lighting dominates the budget by a wide margin — worth treating as its own line item when sizing solar/battery per site, and worth revisiting the dusk-to-dawn baseline (motion-boosted only, no baseline glow) as a lower-power alternative if a site's sun exposure is marginal.

Sizing formula

Battery capacity (Ah) ≥ daily draw (Ah) × autonomy days ÷ usable depth-of-discharge. Example at 3 days of no-sun autonomy, 80% usable DoD on LiFePO4: 3.96 Ah × 3 ÷ 0.8 ≈ 14.9 Ah minimum — round up for margin (e.g. 20 Ah). Solar panel sizing follows from daily Wh needed ÷ average peak sun hours ÷ system efficiency (~0.8 typical for charge-controller + wiring losses).

Sizing standard: size to a conservative worst-case sun-hour assumption (a low-sun winter reference site) rather than tuning per install location — one hardware spec that works everywhere, instead of a per-site solar calculation for every new facility.
Battery chemistry: LiFePO4 recommended over other lithium chemistries for outdoor, unattended, thermally-exposed deployment — more stable under heat and vibration, safer failure mode.
SPEC‑07

Connectivity & data budget

Two very different connectivity profiles live on one site: the controller's telemetry is tiny and infrequent; the camera's video stream is not. Treating them as one connection would size the whole system for the camera's needs.

LinkTechnologyTypical monthly data
Controller telemetryLTE-M or NB-IoT (low-power, low-bandwidth cellular)Low — heartbeats and discrete events, well under 100 MB/month
Camera streamStandard LTE (own SIM, per Sec. 05)High and viewer-dependent — scales with concurrent live viewers and PTZ session length; needs a real per-unit data plan estimate once viewer volume is modeled
Firmware OTAPiggybacks on controller's LTE-M/NB-IoT linkOccasional spikes at update time; scheduled during low-activity windows

Keeping the two links physically and contractually separate (different SIM, different plan) also means a camera data-plan overage on one unit can't starve that unit's alarm/lock reporting.

SPEC‑08

Backend architecture

  • Ingestion: MQTT broker over TLS on a managed IoT platform (e.g. AWS IoT Core or Azure IoT Hub) rather than self-hosted — built-in device identity management and TLS handling, less ops burden at small-to-medium fleet size. Each controller publishes to a per-unit topic namespace (telemetry, discrete events) and subscribes to a command topic for remote arm/disarm or diagnostic requests.
  • Device identity: per-controller certificate or unique API credential issued at commissioning (Sec. 11) — never a shared fleet-wide secret.
  • Data model: time-series storage for continuous telemetry (battery %, heartbeat), a separate discrete event log for alerts (door-open, movement, fault, fire) — different query patterns, different retention needs.
  • Alert rules engine: evaluates incoming events against the same conditions defined in the unit's state machine (Sec. 02) and dispatches notifications — this is the layer the door/lock correlation (Sec. 04) actually runs in.
  • Command path: backend → controller over the same MQTT command topic, with a required acknowledgment; an un-acked command is treated as failed, not assumed delivered.
  • OTA hosting: signed firmware images with staged rollout (a small cohort first) before fleet-wide push.
SPEC‑09

Security model

  • TLS on every link — controller-to-broker, lock-vendor-to-backend, camera-to-backend.
  • Per-device unique credentials, individually revocable — pulling one compromised or decommissioned unit offline should never touch another unit's credentials.
  • Signed firmware images only; controller rejects an unsigned or improperly-signed OTA payload.
  • Rate limiting and anomaly detection on telemetry ingestion — a controller suddenly publishing far outside its normal pattern is itself a signal worth surfacing, not just the individual events.
SPEC‑10

Failure modes & recovery

  • Connectivity loss: local alarm/siren response never depends on the network — it fires from the controller's own state machine. Only the remote notification is best-effort; the physical response is not.
  • Lock/door correlation during an outage (Sec. 04): if the door-open event arrives but no matching lock-unlock event has arrived within the tolerance window — including because the lock vendor's link is down — the default treats it as unauthorized and alerts. A late-arriving lock event after the alert has already fired should reconcile the record, not just get dropped.
  • Battery depletion: a defined power-priority order — alarm and lock-correlation reporting outlast camera and safety lighting as the battery drops, rather than everything degrading uniformly and unpredictably.
  • Firmware crash: hardware watchdog resets the MCU; state re-asserts from local flash rather than defaulting to an unarmed state.
  • Tamper detected: always a local, immediate response regardless of network state — same principle as the alarm.
SPEC‑11

Provisioning & commissioning

  1. Mount controller, sensors, siren, and lighting in the unit; wire to the controller's GPIO/power bus.
  2. Power up; controller runs its BOOT self-test.
  3. Provision device identity — issue the unit's unique certificate/credential and register it with the backend.
  4. Pair the standalone lock and register its vendor account/API access with the backend for correlation (Sec. 04).
  5. Mount and register the cellular camera with the backend relay (Sec. 05).
  6. Run an end-to-end self-test: trigger each sensor, confirm the alert reaches the backend, confirm a test lock event correlates correctly.
  7. Mark commissioning complete; unit enters ARMED_SETUP for its first use.
